Sistema actual · Docker Compose

Arquitectura de la aplicación

El navegador recibe HTML de Angular SSR y consulta la API REST. La administración utiliza la misma API; las sesiones se conservan en PostgreSQL.

  1. ClienteNavegadorRutas públicas y solicitudes API
  2. Contenedor frontendAngular SSRHTML público y navegación
  3. Contenedor backendNestJS · API RESTContenido y administración; sesiones, CSRF y Origin
  4. Acceso a datosPrisma 7Consultas y migraciones
  5. Red de datos aisladaPostgreSQL 18Contenido y sesiones · sin puerto publicado al host

Las tareas de migración y seed se ejecutan antes del backend. Los contenedores de aplicación usan usuario sin privilegios, raíz de solo lectura, tmpfs, capacidades eliminadas y no-new-privileges.

GitHub Actions · Flujo real del workflow

Entrega con identidad comprobada

Después de los checks del repositorio, Gitleaks, la política npm, CodeQL y las pruebas de ambas aplicaciones corren en paralelo. El smoke espera a esos cinco jobs. Dependency Review corre en pull requests y no es una dependencia del smoke.

  1. 01 · SourcePull request o push a main
  2. 02 · Repository checksWhitespace, sintaxis y guardas de base de datos
  3. 03 · Validación en paraleloGitleaks · política npm · CodeQL · backend CI · frontend CIDependency Review se ejecuta solo en pull requests.
  4. 04 · Docker Compose smokeMigración, seed, API, SSR, salud y contenido UTF-8
  5. 05 · Identidad y seguridadIDs inmutables → Trivy sobre esos IDs → tres SBOM CycloneDX ligados a los mismos IDs
  6. Pull request · ValidaciónTermina aquí; no publica imágenes.
  7. Main · PublicaciónExporta y carga las tres imágenes; verifica sus IDs y las publica en GHCR sin reconstruirlas.

El análisis de CodeQL sube resultados. El bloqueo por severidad exige además una regla de GitHub configurada en el repositorio.

Decisiones y límites

Por qué se diseñó así

Sesiones controladas por el servidor

El estado de sesión permanece en PostgreSQL y puede invalidarse desde el servidor. No hacía falta introducir JWT ni registro público.

Base de datos sin acceso público

PostgreSQL solo recibe tráfico por la red de datos de Compose. La API es el límite de acceso para el cliente.

Identidad de imagen antes de publicar

El manifest conserva cada ID probado. Trivy y Syft analizan esos IDs; el job de GHCR verifica los IDs cargados antes de etiquetar y publicar.

Asesoría mysql2 aún abierta · revisión 2026-10-20

mysql2 llega por herramientas de Prisma 7.10.0, que fija la versión afectada. La aplicación usa PostgreSQL, no MySQL. La asesoría sigue visible bajo una excepción específica y temporal que vence el 20 de octubre de 2026. No se aplicó un downgrade forzado ni un override sin soporte; se revisará una actualización compatible de Prisma.
